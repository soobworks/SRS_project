## 순서를 정하는 원칙

1. **기반(Foundation)이 항상 먼저다.** 스키마·인증·외부 API 스위치처럼 다른 모든 태스크가 딛고 서는 것부터 만든다.
2. **"판정 엔진이 가운데"라는 원칙을 그대로 따른다** — SRS_V0_9.md §1.2가 못박은 대로, 판정 없이는 완화도 방문 후보 결정도 시작할 수 없다. 그래서 판정 엔진을 사용자 흐름(초대·후보구성)보다 먼저, **시드 데이터로 먼저 검증**한다(`SRS_V0_9-AI-작업지시서.md` TASK-A1이 FR-009를 1순위로 둔 이유와 동일).
3. **1-A(핵심 검증) 전체를 1-B(제품 완성도)보다 먼저 끝낸다.** 난이도가 가장 높은 영역(양보 문장·완화)은 코어가 검증된 뒤에 붙인다.
4. **횡단 관심사(알림, 전제 공개)는 각 기능 뒤에 얇게 통합한다** — 먼저 만들 대상이 없으면 걸 곳이 없기 때문이다.

## 왜 이 순서인가 — 세 가지 판단 근거 요약

1. **판정 엔진을 화면(사용자 흐름)보다 먼저 검증한다(TASK-003~006).** 가장 난이도 높고 가장 자주 AI 코드생성이 틀리는 영역(검토 보고서 §3)이므로, 실제 사용자 입력 경로가 없어도 시드 데이터로 먼저 정확성을 확인해야 뒤에서 재작업이 줄어든다.
2. **1-A를 다 끝내고 나서 1-B로 넘어간다(TASK-009 이후 게이트).** SRS_V0_9 §10.4의 H1/H3 게이트를 문서상 관행으로만 두지 않고, 태스크 순서 자체에 게이트를 끼워 넣어 "검증 전에 완화·재탐색까지 다 만드는" 스코프 크립을 막는다.
3. **횡단 기능(알림·전제공개·동시접속 상한)은 항상 마지막에 얇게 붙인다.** 걸 대상(액션)이 이미 있어야 걸 수 있기 때문이며, 동시에 이 기능들은 개별적으로 릴리스해도 기존 기능을 깨지 않는 낮은 결합도를 갖는다.
