# [작업 계획] 같이보기 SRS(Next.js 기술스택판) — C-TEC 제약 문구 갱신

**문서 ID:** PLAN-JOINTHOME-NEXTJS-TECDIFF-001

**날짜:** 2026-08-26

**대상 문서:** `같이보기-srs-nextjs-v1_0.md`

**목적:** 사용자가 새로 제시한 C-TEC-001~007 문구를 기존 문서와 대조하고, 두 가지 열린 질문(로컬 DB 선택, LLM 오케스트레이션 조건절 삭제)에 대한 사용자 결정을 반영해 실제 문서 수정 범위를 확정한다.

---

## 1. 배경

이전 턴에서 사용자가 제시한 새 C-TEC-001~007 텍스트를 기존 §1.5와 대조한 결과, 두 지점에서 확인이 필요했다.

1. **C-TEC-003이 중복 제시됨** — "로컬 SQLite"안과 "로컬 Supabase CLI"안이 같은 ID로 함께 제시되어 실제 로컬 개발 DB를 무엇으로 할지 확정되지 않은 상태였다.
2. **C-TEC-005의 조건절 삭제** — 기존 문구의 "(AI 호출 기능이 포함된 경우)"가 새 문구에서 빠지고 "LLM 오케스트레이션은 ... 직접 구현한다"로 단정형이 됐다. 이것이 "LLM을 어떻게 구현할지"에 대한 기술 표준 문구일 뿐인지, 아니면 MVP에 실제 LLM 기능을 새로 넣으라는 뜻인지 확인이 필요했다.

## 2. 사용자 결정 사항

| 질문 | 결정 |
| --- | --- |
| 로컬 개발 DB | **로컬 Supabase CLI 유지** (SQLite안 기각) |
| LLM 오케스트레이션 | **선택적 확장으로 유지** (MVP에 신규 LLM 기반 기능을 넣지 않음) |

두 결정 모두 **기존 문서가 이미 취하고 있던 설계와 동일한 방향**이다 — 즉 이번 작업은 아키텍처·기능을 바꾸는 작업이 아니라, **문서의 제약 문구를 사용자가 확정한 최신 표현으로 정합화**하는 작업이다.

| §1.6 GAP-006 | 옛 조건절 인용 기반 서술 | 조건절 삭제를 인지한 상태로 "기술 표준 ≠ 기능 요구"를 재확인, 재확인 날짜 명시 | 서술 갱신 |

| §6.3, §8.1, §8.2 | "로컬 Supabase" | "로컬 Supabase CLI" | 표현 정밀화 |

**변경하지 않는 것 (No-op 확인)**

- Prisma 스키마(§6.2), ERD, 서비스 모듈 구조(§2.2), Server Actions/Route Handlers 목록(§3): 이미 Supabase CLI(로컬 Postgres) 전제로 작성되어 있어 DB 관련 변경이 필요 없다.
- 기능 요구사항 구현 매핑(§4), 비기능 요구사항(§5): 변경 없음 — LLM을 여전히 호출하지 않으므로 매핑 대상 자체가 그대로다.
- `ADR-TECH-04`(§9): 결정("생성형 AI는 핵심 로직에 미사용")이 그대로 유효해 실질 변경 없음.
- 다이어그램(mermaid) 구조: 노드/화살표 변경 없음, 라벨 텍스트만 일부 정밀화.

## 4. MVP 핵심 사용자 경험(가치 전달) 훼손 여부 검토

PRD §7.1이 정의한 이 제품의 핵심 가치 제안은 다음과 같다.

> "총점이나 AI의 정답 추천 없이 **이번에 보러 갈 집 2개**를 두 사람이 직접 정하도록 돕는 것"

이번 변경이 이 가치 제안에 미치는 영향을 항목별로 검토한다.

| 검토 항목 | 훼손 위험 | 근거 |
| --- | --- | --- |
| 로컬 DB를 Supabase CLI로 유지 | **없음** | 배포 환경은 원래부터 Supabase(PostgreSQL)로 동일했고, 로컬 개발 도구 선택은 사용자에게 노출되는 제품 동작에 전혀 영향을 주지 않는다. 순수 개발자 경험(DX) 영역이다. |
| LLM 오케스트레이션을 선택적 확장으로 유지 | **없음 — 오히려 핵심 가치를 보호하는 결정** | 만약 이번에 LLM을 MVP에 강제로 편입했다면, 판정 엔진·양보 문장 생성이 결정론적 템플릿에서 벗어나 **재현 불가능한 출력**을 낼 위험이 생긴다. 이는 "총점·AI의 정답 추천 없음"이라는 이 제품의 정체성(`decisions/0001`, PRD §15, LIM-03)과 정면으로 충돌한다. 선택적 확장을 유지함으로써 사용자가 매번 같은 조건에 같은 판정 결과를 받는다는 신뢰(REQ-FUNC-020의 재현 가능성 요구)가 그대로 보존된다. |
| C-TEC-005 문구가 단정형으로 바뀐 것 자체 | **문서 정합성 리스크만 있음(제품 리스크 없음)** | 문구가 바뀌었는데 §7.1·§1.6이 옛 문구를 그대로 인용하고 있으면 **문서 내부 모순**이 생긴다. 이것이 실제 위험이며, 사용자 경험이 아니라 "문서를 읽는 개발자가 헷갈릴 위험"이다. 이번 작업(§3의 Diff)으로 해소한다. |

**결론 — 핵심 사용자 경험(가치 전달) 훼손 위험: 없음.**
이번 변경은 아키텍처·기능·데이터 흐름을 전혀 바꾸지 않는 **순수 문서 정합화 작업**이다. 오히려 "LLM을 선택적으로 유지"하는 결정 자체가, 이 제품의 핵심 차별점(결정론적 판정·총점 없음·AI 정답 추천 없음)을 계속 지키겠다는 재확인이라는 점에서 긍정적 신호로 해석할 수 있다.
