## 1. 화면 단위와 PRD 매핑 — T1 확정

### 1.1 결정

**구현 단위는 `SRS_V0_9.md` §2.2의 라우트 7개를 그대로 쓴다. 각 라우트가 담는 PRD 화면 ID·하위 상태를 아래 표로 고정하고, 시나리오 스위처 키를 PRD 화면 ID로 쓴다.**

```
/spaces/demo/judgments?state=A-13b
```

- 구현 구조(라우트)는 SRS를 따르므로 이후 기능 개발과 어긋나지 않는다.
- 검수·리뷰는 PRD 화면 ID로 한다 — "A-13b 확인했나?"가 URL 하나로 답해진다.
- 매핑 표에 없는 화면은 프로토타입에서 만들지 않는다.

> `prototype-suggestion-lite.md` §5의 시나리오 스위처 키(`?scenario=all-unmet` 등)를 **`?state=<PRD 화면 ID>`로 대체**한다. 상태 이름을 새로 짓지 않고 PRD ID를 그대로 쓴다.

### 1.3 이 매핑이 확인해 주는 것

**Scope L(라이트 12건)이 PRD 핵심 와이어프레임 8장 중 7장을 덮는다.** 남은 1장이 `A-13b-2`(재탐색 필터)이고, 그것이 PRD에서 `[TBD]`로 남아 있는 바로 그 화면이다(§7에서 결정).

| 핵심 와이어프레임 | 라우트 | Scope L 커버 |
| --- | --- | --- |
| B-01 · B-02 | `invite/[code]` | ✅ S-003 |
| B-05 | `judgments` | ✅ J-008(B 시점 상태) |
| A-13b | `judgments` | ✅ R-002 ② |
| A-14b | `listings/[id]` | ✅ R-001 |
| A-15a | `listings/[id]` | ✅ R-002 ① |
| A-16e | `visit-selection` | ✅ V-001 |
| **A-13b-2** | `judgments` | ⚠️ PRD `[TBD]` → §7 |

### 1.4 에이전트 준수 규칙

- 화면을 새로 만들 때 **PRD 화면 ID를 먼저 확인**한다. §1.2 표에 없는 화면은 만들지 않는다.
- 시나리오 스위처 키는 **PRD 화면 ID 그대로** 쓴다(`?state=A-13b`). 새 상태 이름을 짓지 않는다.
- 하나의 라우트가 여러 PRD 화면을 담는 것이 정상이다 — 라우트를 쪼개지 않는다.
- 범위 밖(`—`) 화면으로 이어지는 링크는 비활성 또는 "프로토타입 범위 밖" 표시로 둔다. 빈 화면으로 연결하지 않는다.

## 2. 기기 폼팩터 — T2 확정

### 2.1 결정

**폼팩터는 라우트가 아니라 PRD 화면 ID의 접두사가 정한다.**

| 접두사 | 폼팩터 | 기준 폭 | 근거 |
| --- | --- | --- | --- |
| `A-*` | 데스크톱 | 1280px | PRD §17.1 `[확정]` — A는 PC 웹 우선(후보 선택·목록·상세 판정·완화처럼 정보 밀도가 높은 화면) |
| `B-*` | 모바일 | 390px | PRD §17.1 `[확정]` — B는 모바일 우선(카카오톡 링크로 초대 진입) |
| `S-*` | 양쪽 | — | 로딩·계산 불가·경로 없음은 두 폼팩터 모두에서 렌더된다 |

라우트로 규칙을 세우지 않는 이유는 **`B-03`·`B-04`·`B-05`가 `spaces/*` 라우트에 얹히기 때문**이다(§1.2). 라우트 기준으로 잡으면 이 세 화면이 데스크톱으로 나오는데, `B-05`는 PRD가 지목한 핵심 와이어프레임 8장 중 하나이자 모바일 화면이다.

| 화면 ID | 라우트 | 라우트 기본값 | **적용 폼팩터** |
| --- | --- | --- | --- |
| `A-01`~`A-20` | `spaces/*` | 데스크톱 | 데스크톱 |
| `B-01` · `B-02` | `invite/[code]` | 모바일 | 모바일 |
| **`B-03` · `B-04`** | `spaces/[spaceId]/conditions` | 데스크톱 | **모바일** ← 예외 |
| **`B-05`** ★ | `spaces/[spaceId]/judgments` | 데스크톱 | **모바일** ← 예외 |

### 2.2 왜 반응형 한 벌로 가지 않는가

"카톡 링크를 받고 모바일에서 열었을 때 맥락이 읽히는가"는 이 제품의 H1 가설과 직결된다(PRD §17.1이 B의 진입 경로를 명시). 데스크톱 폭에서 보면 그 검증이 성립하지 않는다. 반대로 `A-14`(A/B 대조)와 `A-16e`(Option Grid)는 정보 밀도가 높아 모바일 폭에 접으면 "같은 비중으로 나란히"라는 제약(REQ-FUNC-025)을 눈으로 확인할 수 없다.

### 2.3 구현 규칙

- 폼팩터별 레이아웃을 두 벌 잡되, **컴포넌트는 공유한다** — `BalancedComparison`·`DisclosedValue`는 폭에 따라 배치만 달라진다.
- `B-*` 화면은 뷰포트 폭을 390px로 가정하고 만든다. 데스크톱 브라우저로 열었을 때는 중앙에 390px로 고정 렌더한다(프로토타입 전용 처리, `lib/dev/`에 둔다).
- 반응형 브레이크포인트를 촘촘히 만들지 않는다. **두 폭만** 성립하면 된다.

## 3. 네이버 셸 — T3 확정

### 3.1 결정

**네이버를 흉내 내지 않는 중립 셸을 두고, 우리 기능의 경계와 이탈 지점만 표시한다.**

PRD §17.1 `[확정]` — "제품 형태는 별도 앱이 아니라 네이버 앱/서비스 안의 기능이다." 검수 질문("네이버 안의 기능으로 읽히는가")에 답하는 데 필요한 것은 **경계 표시**지 외형 복제가 아니다.

### 3.2 셸 구성

| 요소 | 내용 |
| --- | --- |
| 파일 | `components/dev/prototype-shell.tsx` — 프로토타입 전용, `lib/dev/`와 함께 삭제 대상 |
| 상단바 | 중립 회색. 텍스트 브레드크럼 `네이버 부동산 › 같이 고르기` 한 줄 |
| 데스크톱(`A-*`) | 상단바 + 본문 1280px |
| 모바일(`B-*`) | 390px 프레임 상단에 축약 바(`‹ 같이 고르기`) |
| 이탈 지점 | 점선 테두리 + `네이버 탐색으로 나감 (프로토타입 범위 밖)` 배지 |

### 3.3 이탈·진입 지점 표시 대상

§1.2에서 "범위 밖(`—`)"으로 표시된 화면 중 **네이버 본체로 넘어가는** 지점이다. 링크를 비활성으로 두지 말고 이 배지로 표시한다 — 이 제품이 자기 화면만으로 완결되지 않는다는 것 자체가 검수 대상이기 때문이다.

| 지점 | 화면 | 표시 |
| --- | --- | --- |
| 진입 | `A-01` 기능 진입 | `네이버 부동산 관심매물에서 들어옴` 배지 |
| 이탈 | `A-13b-2` 재탐색 필터 → 네이버 탐색 | `이 필터로 찾아보기` 버튼 누르면 배지로 대체(실제 이동 없음) |
| 이탈·복귀 | `A-20` 매물 추가·교체 | 배지만, 링크 없음 |

### 3.4 금지

- **네이버 로고·CI 색상·상표·실제 UI 마크업을 사용하지 않는다.** 텍스트 브레드크럼만 쓴다.
- 저장소 루트의 기존 HTML 시안 중 네이버 헤더를 복제한 부분을 가져오지 않는다.
- 이 프로토타입이 실제 네이버 서비스 화면으로 오인될 수 있는 형태로 외부 공유하지 않는다.

## 4. 판정 표시 문법 — T4 확정

### 4.1 5분류 상태 — 라벨·기호·색 역할

SRS enum `JudgmentStatus`와 PRD §18.3 문구를 1:1로 고정한다. **에이전트가 라벨을 새로 짓지 않는다.**

| enum | 사용자 대면 라벨 | 기호 | 색 역할 | PRD §18.3 정의 |
| --- | --- | --- | --- | --- |
| `MET` | `충족` | `✓` | 충족색 | — |
| `UNMET` | `미충족` | `✗` | 미충족색 | 재봤고 기준에 못 미침 |
| `CONFIRMATION_NEEDED` | `확인 필요` | `?` | 확인색(**별도 배지**) | 데이터가 없어 확인 필요 |
| `CALCULATION_FAILED` | `계산 불가` | (기호 없음) | 중립 회색 | 재려 했지만 실패 |
| `NOT_APPLICABLE` | `해당 없음` | (값 없음) | 중립 회색 | 잴 대상 자체가 없음 |

3분류 그룹 라벨(PRD §13.2): `둘 다 충족` / `한쪽만 충족` / `둘 다 불충족`. **`확인 필요`는 이 3분류 중 하나로 흡수하지 않고 별도 배지로 병기한다**(AC-11-02).

색 역할(PRD §13.3): **색은 충족·미충족·확인 상태에만 쓴다. A/B 구분은 위치와 라벨로만 한다.** 지도 경로선만 예외로 동일 굵기·투명도의 색을 A/B에 쓸 수 있다.

### 4.2 `해당 없음` 행 처리 — 틀리기 쉬운 지점

`NOT_APPLICABLE`은 "행 제거"라고만 알면 절반이 틀린다. PRD §19.2가 A·B를 나눠 규정한다.

| 상황 | 처리 | 근거 |
| --- | --- | --- |
| **둘 다** 해당 없음(둘 다 출퇴근 안 함) | **행 자체를 제거**한다 | §19.2 "교통비 항목 자체를 표시하지 않음" · §18.3 "행 제거" |
| **한쪽만** 해당 없음 | **행은 유지**하고 해당 없는 쪽 칸에 `해당 없음`을 표시한다 | §19.2 "해당 사용자 교통비만 포함" |

**출퇴근하지 않는 사람의 통근비를 `0원`으로 계산하지 않는다**(§19.2 명시). `0`은 값이고 `해당 없음`은 값이 아니다.

### 4.3 조건 한 줄 표기 — 화면별 이원화

| 형식 | 쓰이는 화면 | 목적 |
| --- | --- | --- |
| **축약형** | `A-12`·`A-13`·`A-13c`(목록) · `B-05`(B 첫 결과, 모바일) | **누구에게 무엇이 문제인지**를 한눈에 읽는다 |
| **전체형** | `A-14`·`A-14a~e`(상세) · `A-15`(완화) · `A-16e`(Option Grid) | **판정 근거 전부**를 보여준다 |
| **문장 내 삽입** | `A-14b`(양보 문장) | `…통근을 3분 더 감수하고…` |

#### 축약형 — 목록(`A-13`)

```text
흑석 한강센트레빌
한쪽만 충족
A · 통근 +3분
B · 예산 +월 7만
```

- 매물명 → 3분류 라벨 → **사람별 한 줄**(`A · <조건명> <미달량>`) 순서.
- 사람 접두어(`A ·` / `B ·`)를 붙여 **누구의 문제인지**를 명시한다.
- **미충족 조건만** 싣는다(PRD §17.2 A-13 "인라인 미달 요약"). 조건 순서(§4.5)상 앞 2개까지, 나머지는 `외 N개`로 접는다.
- A·B 두 줄을 **항상 같은 형식·같은 줄 수**로 둔다. 한쪽이 미충족 0개면 `A · 전부 충족`으로 빈 줄을 메워 시각 비중을 맞춘다.
- 임계값은 싣지 않는다 — 목록의 목적은 "무엇이 걸리는가"이지 "얼마 기준인가"가 아니다.

#### 전체형 — 상세(`A-14`)

```text
A
예산  92만 ≤ 100만  ✓
통근  13분 > 10분   ✗ +3분
면적  68㎡ ≥ 60㎡    ✓
주차  없음          ✗

B
예산  92만 > 85만   ✗ +월 7만
통근  22분 ≤ 30분   ✓
면적  68㎡ ≥ 55㎡    ✓
주차  있음 기준 없음  —
```

- **사람 블록** 단위다. A 블록과 B 블록을 동일 순서·동일 형식으로 둔다(데스크톱: 좌우 2열, 모바일: 상하).
- **충족 조건도 전부 싣는다.** 미충족만 보여주면 "무엇을 얻는지"가 사라진다.
- 구성: `조건명 · 실제값 (비교기호) 임계값 · 판정기호 미달량` — PRD §13.2 예시(`13분 > 10분 ✗ +3분`) 그대로.
- 한 사람이 걸지 않은 조건은 그 사람 블록에서 기준 없음으로 두되 **행을 지우지 않는다** — 블록 간 행 수가 달라지면 시각 비중이 깨진다.

미달량 표기는 PRD §12.3 `미달 표현` 열을 그대로 쓴다.

| 조건 | 타입 | 미달 표기 |
| --- | --- | --- |
| 예산 | 상한형 | `+월 15만` |
| 통근시간 | 상한형 | `+7분` |
| 역 도보 | 상한형 | `+3분` |
| 전용면적 | 하한형 | `−7㎡` |
| 주차 | 유무형 | `없음` |
| 매물 유형 | 일치형 | 실제 매물값(`빌라`) |

### 4.4 축약형이 임계값을 잃는 문제 — 보완 규칙

축약형에는 임계값이 없다. 이는 **의도된 정보 축약**이며, 아래로 메운다.

1. **축약형은 언제나 전체형이 있는 화면으로 가는 진입점이다.** 목록 카드는 `A-14`(상세)로 연결한다. 막다른 축약형을 만들지 않는다.
2. 축약형을 **미달량 크기로 정렬하지 않는다** — 조건 순서(§4.5)를 그대로 따른다. 정렬은 §9에서 별도 결정.
3. 축약형이 미충족만 고르는 것은 §4.5의 "A/B 행 순서를 다르게 만들지 않는다" 제약과 충돌하지 않는다 — 순서를 바꾸는 게 아니라 같은 순서에서 필터링하는 것이다.

### 4.5 조건 순서 — 고정

```
예산 → 통근 → 추가 필수① → ② → ③ → ④ → 확인 필요
```

- PRD §13.2 `[확정]`. 전체형·축약형·양보 문장 **전부 이 순서**를 쓴다.
- **미충족 조건을 위로 올려 A/B 행 순서를 다르게 만들지 않는다.** A 행과 B 행은 언제나 같은 순서다.
- 축약형이 미충족만 고르는 것은 이 제약과 충돌하지 않는다 — 순서를 바꾸는 게 아니라 같은 순서에서 필터링하는 것이다.

### 4.6 금지

- 5분류·3분류 라벨을 다른 말로 바꾸지 않는다(`부적합`·`아쉬움`·`보통` 등).
- `✓`/`✗` 외의 평가 기호(별점·이모지·게이지)를 쓰지 않는다.
- 조건별 상태를 **합산·평균·점수화**하지 않는다. 3분류는 A·B 각 5분류의 조합 결과이지 집계값이 아니다.
- `확인 필요`를 미충족으로 접거나 3분류 안에 넣지 않는다.

## 5. 전제 공개 범위 — T5 확정

### 5.1 결정

**`DisclosedValue`는 PRD §19.3 전제에 의존하는 값만 감싼다. 인라인 툴팁은 기준 시점 한 줄로 짧게 두고, 전제 11종 전문은 `A-04a` 전제 패널에 모아 정본으로 삼는다.**

PRD §19.5의 허용 표현 `월 약 92만원으로 추정됩니다 · 전제 보기`가 정확히 이 구조다 — "전제 보기"가 패널로 가는 링크다.

### 5.2 숫자 4분류 — 무엇을 감싸는가

| 분류 | 예 | `DisclosedValue` | 표시 |
| --- | --- | --- | --- |
| **추정치**(전제 의존) | 월 실질 주거비, 실부담 6항목, 교통비 | ✅ 감싼다 | `약 92만ⓘ` — **`약` 접두어 필수**(§19.5) |
| **추정치 파생** | 예산 미달량 `+월 7만` | ✅ 감싼다 | 원본이 추정치면 파생도 추정치다 |
| **실측치** | 통근 13분, 면적 68㎡, 역도보 5분, 매물 보증금·월세 | ❌ | 평문. 필요 시 출처 라벨(`경로 계산 기준`) |
| **사용자 입력값** | 예산 상한 100만, 통근 임계 10분 | ❌ | 평문 |
| **실측 파생** | 통근 미달량 `+3분` | ❌ | 원본 둘이 평문이므로 근거가 이미 선다 |

**판별 기준 한 줄:** 그 숫자가 §19.3 전제표의 값이 바뀌면 함께 바뀌는가? 바뀌면 추정치다.

### 5.3 인라인 툴팁

```text
예산  약 92만ⓘ ≤ 100만  ✓

ⓘ →  기준 2026-06 · 전제 보기
                     └→ A-04a
```

- 툴팁 본문은 **기준 시점 + `전제 보기` 링크**만. 전제 내용을 툴팁에 복제하지 않는다.
- **ⓘ는 행당 최대 1개.** 한 줄에 전제 의존 값이 둘 이상이면(`약 92만` + `+월 7만`) 첫 값에만 단다.
- 목록 축약형(§4.3)에서도 같은 규칙을 쓴다 — `B · 예산 +월 7만ⓘ`.

### 5.6 `[TBD]` 항목의 프로토타입 처리

관리비 별도 항목 추정 범위가 PRD에서 `[TBD]`다. 프로토타입은 **빈칸을 메우지 않고 표시한다.**

- 실부담에는 **표시 관리비만** 반영한다.
- 별도 항목(수도·난방 등)은 `확인 필요` 배지로 두고 추정값을 만들지 않는다.
- 전제 패널 11번 행에 `[TBD] 추정 범위 미확정`을 그대로 노출한다.

| `대출 가능액은 1억 2천입니다` | 확정 한도를 제시하지 않는다 |

### 5.8 ESLint 규칙(원 순번)에 남기는 것

`X-001`의 N-005 흡수분은 원 순번에서 구현한다(라이트 범위 제외). 다만 **판별 범위는 여기서 정한다** — 정적 분석으로 "전제 의존"을 알 수 없으므로, 추정치를 전용 타입으로 감싸 타입 시스템이 1차 방어하고 ESLint는 보조로 둔다. 타입 도입 여부는 `C-001` 원 순번의 결정 사항이다.

## 8. 선호 카드 — T8 확정

### 8.1 결정

**픽스처 문장을 조건 세트에 넣고 표시만 한다. 입력 UI(`A-08`)는 만들지 않는다**(`I-002` 원 순번).

선호는 PRD §12.4·`I-002`가 정한 대로 **판정 로직에 어떤 형태로도 연결되지 않는 자유 문장**이다. 로직이 없으므로 픽스처 문자열만으로 화면이 성립한다.

### 8.2 픽스처 문장 — `lib/dev/scenarios.ts`

| 사람 | 선호 문장 |
| --- | --- |
| A | · 햇빛 잘 드는 집이면 좋겠어요<br>· 3층 이상이면 좋겠어요<br>· 가까운 곳에 마트가 있으면 편해요 |
| B | · 조용한 동네였으면 해요<br>· 분리형 구조면 좋겠어요 |

`solo` 세트에서는 B가 없으므로 B 카드도 없다. A·B 문장 수를 일부러 다르게(3개/2개) 뒀다 — 개수가 달라도 카드 비중이 흔들리지 않는지 확인하기 위해서다.

### 8.3 표시 위치

| 화면 | 표시 |
| --- | --- |
| `B-02` ★ | **A의 선호 카드**. PRD §17.3이 이 화면의 정의로 명시 — 후보 5개와 함께 조건 입력 **전**에 보여준다 |
| `A-13` | A·B 선호 카드를 **사람 단위로 한 번씩**. PRD §17.2 A-13의 구성 요소 |

### 8.4 금지 — 검수 대상

PRD §13.2 `[확정]` · §12.4가 못박은 것이다. 프로토타입에서 이 규칙이 지켜지는지 **눈으로 확인할 대상이 생긴다**는 것이 선호 카드를 넣는 주된 이유다.

- 선호를 **매물 비교표에 넣지 않는다.** 사람 단위 카드로 한 번만 보여준다.
- 매물별 **✓/✗를 붙이지 않는다.**
- 판정 쿼리에 조인하지 않는다(프로토타입에서는 픽스처가 분리돼 있으므로 구조적으로 불가능하다).
- 선호 문장을 판정 결과·양보 문장·완화 제안에 인용하지 않는다.

## 9. 정렬 UI — T9 확정

### 9.1 결정

**프로토타입에 정렬을 넣지 않는다.** 3분류 그룹으로만 묶고, 그룹 내부는 **후보를 담은 순서**(`L-001`→`L-005`)로 고정한다.

```text
A-13  후보 목록

■ 둘 다 충족 (1)
   L-004 사당 그린홈

■ 한쪽만 충족 (1)
   L-001 흑석 리버뷰

■ 둘 다 불충족 (3)
   L-002 상도 파크빌
   L-003 노량진 스카이
   L-005 신대방 코지
```

### 9.2 근거

PRD §13.3은 정렬을 **금지하지 않고 조건부로 허용**한다("단일 조건 값 또는 `한쪽만 충족` 그룹 안의 실제 미달량 기준 정렬은 가능하며, 정렬 기준을 화면에 밝힌다"). 그럼에도 프로토타입에서 빼는 이유는 셋이다.

1. **검증할 재료가 없다.** `normal` 세트의 `한쪽만 충족` 그룹은 `L-001` 1건뿐이다(§6.6). 정렬을 만들어도 눈에 보이지 않는다.
2. **검수 대상이 아니다.** `prototype-suggestion.md` §5.2의 검수 질문 8개 어디에도 정렬이 없다. PRD도 "가능"이라 했지 "필수"라 하지 않았다.
3. **총점이 스며드는 통로다.** 정렬 드롭다운은 `종합순`·`추천순` 옵션이 무심코 추가되는 가장 흔한 지점이다(`prototype-suggestion.md` §10 R4).

실데이터가 붙어 `한쪽만 충족`이 여러 건 나오는 시점(`J-006` 원 순번)에 판단하는 것이 순서에 맞다.

### 9.3 금지

- 정렬 컨트롤(드롭다운·탭·토글)을 **만들지 않는다.**
- 그룹 내부를 미달량·실부담·면적 등 어떤 값으로도 재정렬하지 않는다.
- 3분류 그룹의 **표시 순서**는 `둘 다 충족 → 한쪽만 충족 → 둘 다 불충족`으로 고정한다. 이는 정렬이 아니라 그룹 정의 순서다(PRD §13.2).

> §4.4의 "축약형을 미달량 크기로 정렬하지 않는다"는 **한 매물 안의 조건 줄 순서**에 대한 규칙이고, 이 절은 **매물 목록의 순서**에 대한 규칙이다. 층위가 다르며 둘 다 "재정렬하지 않는다"로 같은 결론이다.
