## 2. 병합 기준 (무리하지 않는 선)

병합은 아래 **셋 중 하나 이상**을 만족할 때만 후보로 삼았다. 하나도 만족하지 않는 Task는 절대 건드리지 않았다.

1. **같은 파일·같은 엔티티** — 두 Task가 결국 같은 소스 파일이나 같은 DB 테이블을 다룬다(예: 4개 조건 평가기가 전부 `domain/judgment/evaluators/` 아래 같은 패턴).
2. **AC가 이미 하나로 묶여 있음** — 원 SRS §9 자체가 두 기능의 AC를 같은 절(§9.x)에 함께 서술하고 있거나, v2에서 이미 테스트 companion을 공유하고 있다(예: TEST-J-EXT가 이미 5개 Task를 하나로 검증 중).
3. **개별 복잡도가 낮음(L)** — 어느 하나만으로는 독립 GitHub Issue로 두기엔 내용이 몇 줄 안 된다(예: 판정 결과 upsert 한 줄짜리 저장 로직).

**원칙을 지키기 위해 병합하지 않은 것:** V-001(2라운드 매칭)과 V-002(균형 렌더링)는 둘 다 "낮은 복잡도"처럼 보일 수 있지만 백엔드 로직 vs 프론트엔드 렌더링이라는 서로 다른 에이전트 컨텍스트라 병합하지 않았다. S-002(초대 발급)와 S-003(B 맥락 조회)도 원 SRS상 FR-005·006으로 애초에 별개 요구사항이라 병합 후보에서 제외했다. Phase 0(C-000/001/002)은 원칙 1의 "DB/API 계약/Mock 데이터 3분리"를 사용자가 준 방법론 원문이 명시적으로 요구하므로 병합하지 않았다.
