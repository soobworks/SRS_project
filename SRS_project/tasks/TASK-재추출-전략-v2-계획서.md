# TASK 재추출 전략 v2 — 계약 우선 · Closed Context · AC 자동화 테스트

**문서 ID:** ROADMAP-JOINTHOME-TASKGEN-002

**날짜:** 2026-08-26

**목적:** 기존 21개 TASK(`SRS_project/tasks/TASK-000~020`)를 아래 3원칙에 따라 재평가하고, 원칙을 충족하도록 재구성한 새 태스크 목록을 확정한다. 이 문서는 계획이며, **전체 태스크 본문은 아직 다시 쓰지 않았다.**

---

## 적용할 3원칙

1. **계약(Contract) 우선** — 기능·화면보다 DB 스키마·DTO·Mock 데이터를 먼저, 독립 Task로 추출한다(SSOT 확보).
2. **상태 변경 기준 Closed Context 분리** — Read/Query와 Write/Command를 하나의 Task에 섞지 않는다.
3. **AC → 자동화 테스트 Task 변환** — 인수 조건을 체크리스트로 남기지 않고, "이 테스트가 통과할 때까지 로직을 수정하라"고 명령할 수 있는 별도 Task로 뽑는다.

### Phase 9 — AC 자동화 테스트 Task (신규)

원 SRS(`같이보기-srs-v1_0.md` §9)의 61개 AC를 자동화 테스트 Task로 변환한다. **granularity(세분화 수준)에 대한 선택이 필요하다** — 아래 두 옵션의 결과물 규모가 3배 가까이 차이 난다.

| 옵션 | 방식 | 결과 Task 수 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| **A. AC 1개 = Task 1개(완전 원자화)** | "AC-10a-02: 계산 불가 분리 검증" 같은 단위로 61개 개별 Task | **61개** | 원칙 3의 예시("400 에러 검증 Task")와 가장 정확히 일치, 에이전트에게 가장 좁고 명확한 컨텍스트 제공 | Task 하나가 테스트 코드 몇 줄에 불과해 관리 오버헤드가 큼. GitHub Issue 61개가 거의 전부 "한 줄짜리" |
| **B. 기능 Task당 테스트 Task 1개(companion)** | 위 Phase 0~8의 36개 기능 Task 중 원 SRS에 대응 AC가 있는 것마다 "-TEST" companion Task 1개, 그 안에 관련 AC들을 개별 테스트 항목으로 나열 | **약 22개**(대응 FR이 있는 태스크 기준) | Task 수가 합리적, 그래도 "체크리스트가 아니라 테스트 작성 Task"라는 원칙 3의 핵심은 유지(Task Breakdown 자체가 "AC-X 테스트 작성"으로 구성됨) | AC 하나하나의 원자성은 옵션 A보다 약함 |

**권장:** 옵션 B. 이유 — 원칙 3의 핵심은 "AC가 사람이 읽는 체크리스트로 남지 않고, 에이전트가 스스로 판정할 수 있는 자동화된 기준이 되어야 한다"는 것이다. 이는 Task 자체가 "테스트를 작성하라"는 명령형인지가 핵심이지, AC 1개당 Task 1개가 핵심은 아니다. 다만 이 판단은 사용자 확인이 필요하다.

**옵션 B 채택 시 최종 규모:** 36(기능/인프라) + 22(테스트 companion) = **58개 Task**(기존 21개 대비 2.8배)
**옵션 A 채택 시 최종 규모:** 36 + 61 = **97개 Task**(기존 21개 대비 4.6배)

## 3. 작성 순서(신규)

```
Phase 0 (계약)   : C-000 → C-001 → C-002
Phase 1 (인증)   : A-001
Phase 2 (판정)   : J-001 → J-002 → J-003 → J-004 → J-005 → J-006 → J-007 → J-008 → J-009
Phase 3 (입력)   : I-001 → I-002
Phase 4 (공유객체): S-001 → S-002 → S-003 → S-004 → S-005
Phase 5 (방문후보): V-001 → V-002 → V-003   ※ V-001 완료 = 1-A 완료, H1/H3 게이트
Phase 6 (완화)   : R-001 → R-002 → R-003 → R-004 → R-005
Phase 7 (횡단)   : X-001 → X-002 → X-003 → X-004
Phase 8 (단계2)  : F-001 → F-002 → F-003
Phase 9 (테스트) : 각 기능 Task 완료 직후 해당 테스트 Task를 바로 이어 실행(TDD 정신 유지)
Phase 10 (배포)  : D-001
```

Phase 9(테스트)를 맨 뒤에 몰아두지 않고 **각 기능 Task 바로 다음에 배치**한 이유: 원칙 3의 취지("테스트가 통과할 때까지 로직 수정")를 살리려면 테스트가 구현과 분리된 채 나중에 오면 안 되고, 구현 직후(이상적으로는 구현 직전, TDD)에 와야 한다.
