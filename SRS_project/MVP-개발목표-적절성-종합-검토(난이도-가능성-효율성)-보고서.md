## 1. 검토 대상 및 범위

`같이보기-srs-nextjs-v1_0.md`는 같이보기 SRS v1.0(마이크로서비스, 기술 중립적)의 기능 요구사항을 그대로 유지하면서, 아래 기술스택(C-TEC-001~007, `같이보기-srs-nextjs-기술스택변경-plan-v1_0.md` 반영 완료)으로 실제 구현 가능한 형태로 재작성한 문서다.

- Next.js(App Router) 단일 풀스택 + Server Actions/Route Handlers
- Prisma + 로컬 Supabase CLI → 배포 Supabase(PostgreSQL)
- Tailwind CSS + shadcn/ui
- Vercel AI SDK + Google Gemini (선택적 확장)
- Vercel 배포, Git Push 자동화

이 보고서는 이 스택 전제 하에 "MVP를 실제로 완주할 수 있는가"를 다섯 개의 하위 질문으로 쪼개 검토한다.

## 4. 효율성 검토 (신규)

### 4.1 개발 속도 — MVP 단계의 과도한 시간 소요를 피하는가

**현재 상태:** SRS §14.1(단계 1 — 검증 코어)는 FT1~FT7, REQ-FUNC-001~021·024·025로 **25개 중 21개 요구사항**을 포함한다. "검증 코어"라는 이름과 달리 실질적으로는 거의 완제품에 가까운 범위다.

**좋은 안전장치가 이미 있음:** §10.4의 릴리스 게이트는 단계 1 착수 전에 **코드를 한 줄도 안 쓰는 H1 선행 측정**(조건 대조 로직 없이 목록 공유 + 최소 반응)을 요구한다. 이는 "만들기 전에 검증"이라는 원칙을 잘 지키고 있다.

**그럼에도 남는 문제 — 단계 1 통과 이후:** H1 게이트를 통과한 다음 순간, 팀은 곧바로 21개 요구사항 전체를 향해 달리게 된다. 이 사이에 **"단계 1 안의 단계"**가 없다. 아래처럼 한 번 더 쪼개는 것을 권고한다.

| 서브 단계 | 포함 요구사항 | 근거 |
| --- | --- | --- |
| **1-A (핵심 검증)** | FR-01,02,05,06,09,10A,10B,11,17,20,25 | "조건 입력 → 판정 → 방문 후보 2개 확정"이라는 North Star(§10.1) 달성에 필요한 최소 경로. 완화·재탐색·전제공개·알림 없이도 H1/H3 가설(§12.3) 검증이 가능하다 |
| **1-B (제품 완성도)** | FR-03,04,07,08,12~16,18,19,21,24 | 위 경로가 실측으로 검증된 뒤에만 투자. 특히 FR-12~16(양보 문장·완화)은 개발 난이도가 가장 높은 영역이므로 핵심 경로가 먼저 검증된 뒤 투입하는 것이 리스크 분산 효과가 크다 |
| 단계 2 (기존과 동일) | FR-22,23 | 변경 없음 |

이렇게 쪼개면 "단계 1 전체가 끝나야 사용자 반응을 본다"가 아니라 **"1-A만 끝내도 North Star를 실측할 수 있다"**로 바뀌어, MVP 단계의 시간 소요를 실질적으로 줄일 수 있다.

**추가로 시간을 잡아먹을 숨은 작업(현재 견적에 없음):**

- 네이버 API 3종에 대한 **목업 데이터 레이어** 설계·구현 — GAP-001로 인해 실제 API 연동이 불가능한 이상, 이 목업 자체가 별도 작업량이지만 현재 어느 견적에도 반영돼 있지 않다.
- 인증 프로바이더 미확정(GAP-002)에 따른 **임시 인증 설계** — 아래 4.2에서 구체적 대안을 제시한다.

### 4.2 외부 연동 목표와 기술 스택 — 복잡성·오픈소스 여부에 따른 적절성과 리스크

**구성요소별 오픈소스·포터빌리티 평가**

| 구성요소 | 오픈소스 여부 | 복잡성 | 평가 |
| --- | --- | --- | --- |
| Next.js | 오픈소스(MIT), 타 호스트로 이전 가능 | 낮음(App Router 학습곡선은 있음) | 적절 |
| Prisma | 오픈소스, 벤더 종속 없음 | 낮음 | 적절 |
| Tailwind CSS · shadcn/ui | 오픈소스, shadcn은 코드 복사 방식이라 종속 자체가 없음 | 낮음 | 매우 적절 — MVP 디자인 시스템을 직접 구축하는 시간을 절약 |
| Supabase | 코어는 오픈소스(셀프호스팅 가능), 관리형 서비스 이용은 벤더 종속 | 중간 | 적절 — 단, Auth 프로바이더 이슈는 아래 별도 논의 |
| Vercel(플랫폼) | **비공개(폐쇄형 SaaS)** | 낮음(설정 부담 최소화가 목적) | **의식적 트레이드오프로 인정 가능하나 문서에 명시 필요** — Cron Job·Analytics 등 Vercel 특화 기능을 쓸수록 타 플랫폼 이전 비용이 커진다 |
| Vercel AI SDK | 오픈소스(`ai` 패키지) | 낮음 | 적절, 현재 미사용이라 리스크 없음 |
| Gemini API | 비공개(모델·API 모두 폐쇄형) | 낮음(호출만 하므로) | 낮은 리스크 — 미사용 상태 유지 시 영향 없음 |
| 네이버 관심매물·경로·검색 API 3종 | 비공개, **접근권 자체 미확보** | 해당 없음(호출 불가) | **가장 큰 리스크 — 아래 참고** |

**총평:** 프레임워크·ORM·스타일링·DB 코어는 대부분 오픈소스라 벤더 종속 리스크가 낮다. Vercel·Supabase·Gemini는 관리형 서비스를 택해 "인프라 설정 복잡도 최소화"(C-TEC-003·007의 취지)라는 목표에는 정확히 부합하는 합리적 선택이다. **다만 이 선택이 트레이드오프라는 사실 자체가 SRS 어디에도 명시돼 있지 않다** — "왜 Vercel인가"에 대한 ADR은 있지만(§9), "Vercel을 벗어나려면 무엇을 다시 짜야 하는가"는 문서화돼 있지 않다.

**조정 권고 — 목업 레이어를 공식 설계 요소로 승격**

현재 §3.3(외부 시스템 연동)은 네이버 API 3종을 실제 존재하는 것처럼 클라이언트 인터페이스만 정의한다. 접근권이 없다는 사실(GAP-001)과 실제 구현 설계 사이에 공백이 있다. 아래처럼 목업 스위치를 추가하는 것을 권고한다.

```
lib/external/
  naver-listing.ts       # 실제 클라이언트 (접근권 확보 후)
  naver-listing.mock.ts  # 고정 픽스처 기반 목업
  index.ts               # NAVER_API_MODE=mock|live 환경변수로 분기
```

이렇게 하면 네이버 연동 여부와 무관하게 나머지 21개(또는 1-A의 11개) 요구사항을 실제로 동작시키고 검증할 수 있다 — 이것이 개발 속도(4.1)와 리스크 완화를 동시에 잡는 지점이다.

**조정 권고 — 인증을 "임시 방편"으로 명시적으로 낮추기**

GAP-002(네이버 OAuth의 Supabase Auth 지원 여부 미확정)를 해결하기 전까지, 아래 대안 중 하나를 **1-A 단계의 공식 임시 설계**로 채택하는 것을 권고한다.

| 대안 | 장점 | 비용 |
| --- | --- | --- |
| Supabase Auth 매직 링크(이메일) | Supabase 표준 기능, 네이버 종속 없음 | 실제 "네이버 로그인"이라는 제품 맥락과는 다름(단계 1-A는 검증용이므로 허용 가능) |
| 초대 코드 자체를 B의 임시 신원으로 사용 | 별도 인증 시스템 자체가 불필요, REQ-FUNC-007의 임시 조건 저장 구조를 그대로 재사용 | 계정 개념이 없어 FR-08(결과 후 로그인)은 이 단계에서 검증 불가 — 1-B로 이월 |

둘 다 "네이버 로그인이 확정될 때까지 개발이 멈추는" 상황을 막는다는 점에서 개발 속도(4.1)에 직접 기여한다.

### 4.3 운영 소요 비용 — 클라우드 컴퓨팅 서비스 기준 추정

> 아래 수치는 **2026년 8월 기준 각 서비스의 공개된 무료/유료 티어 구조에 대한 일반적 이해를 바탕으로 한 정성적 추정**이며, 정확한 금액·한도는 배포 직전 각 서비스의 공식 가격 페이지에서 반드시 재확인해야 한다(가격 정책은 수시로 바뀐다). 이 문서에서는 확정 수치 대신 **비용을 견인하는 요인**과 **무료 티어로 버틸 수 있는 범위**를 정리한다.

**H1 검증 규모 기준 (초대 발송 30건 또는 4주, SRS §24.4) — 사실상 무료로 운영 가능**

| 항목 | 비용 견인 요인 | H1 규모에서의 추정 |
| --- | --- | --- |
| Vercel 서버리스 함수 | 요청 수 · 실행 시간 | 초대 30건 수준이면 무료 티어(Hobby) 한도에 크게 못 미침 |
| Supabase DB | 저장 용량 · 동시 연결 수 | 수백 행 규모로 무료 티어 한도(수백 MB) 내 |
| Supabase Auth | MAU(월간 활성 사용자) | A·B 두 사람 × 검증 세션 수 = 무료 티어로 충분 |
| Gemini API | 토큰 사용량 | §7 결정대로 미사용 유지 시 **$0** |
| Vercel Cron Job | 실행 빈도 | GAP-003에서 지적한 폴링 주기와 직결 — 빈도를 올릴수록(예: 매물 소진 감지를 "즉시"에 가깝게 하려 할수록) 무료 한도 소진이 빨라진다. **비용과 실시간성은 트레이드오프 관계**임을 명시해 둔다 |

**비용보다 먼저 챙겨야 할 두 가지 운영 리스크**

1. **Vercel Hobby 티어의 상업적 이용 제약** — 많은 서버리스 플랫폼의 무료 티어는 "비상업적 용도"를 전제로 하는 경우가 흔하다. 이 프로젝트가 실습을 넘어 실제 서비스로 이어질 가능성이 있다면, **어느 시점에 Pro 플랜으로 전환해야 하는지를 결정 기준(예: "실사용자 유입 확정 시" 또는 "H1 게이트 통과 시")으로 미리 문서화**해 두는 것을 권고한다. 정확한 약관은 배포 전 재확인이 필요하다.
2. **Supabase 무료 프로젝트의 비활동 휴면** — 관리형 무료 DB는 일정 기간 트래픽이 없으면 자동 일시정지되는 경우가 흔하다. 검증 주기가 4주 단위로 느슨한 이 프로젝트 특성상, 데모·투자 미팅 직전에 "깨어나지 않는" 상황을 피하려면 배포 전 해당 정책을 확인해 둘 필요가 있다.

**비용이 실제로 문제가 되는 시점 — H1 이후**

H1이 통과해 단계 1(또는 1-A/1-B)로 넘어가고 실사용자가 유입되기 시작하면, 무료 티어 한도(DB 용량, 함수 실행 시간, Auth MAU)를 넘길 가능성이 생긴다. 이 시점부터는 §10.1의 North Star·가드레일 지표 실측치를 근거로 유료 전환 여부를 판단하면 되므로, **지금 시점에 유료 비용을 미리 설계에 반영할 필요는 없다** — 다만 "언제 유료 전환을 검토할지"의 트리거 조건(예: DAU N명, DB 용량 N% 도달)을 §10.3(관측 항목)에 추가하는 것은 유효한 개선점이다.

## 6. 결론

같이보기 SRS(Next.js 기술스택판)는 **기술스택 선택 자체는 MVP 검증 목적에 합리적이며 운영 비용도 현재 검증 규모에서는 사실상 무료**다. 그러나 "조정할 것이 없는가"라는 질문에는 **그렇지 않다**고 답한다 — 특히:

1. 단계 1의 스코프가 이름과 달리 크다 (4.1)
2. 네이버 API·인증이라는 두 외부 차단 요소에 대한 **대체 설계가 문서에 없다** (4.2) — 이는 GAP-001·002를 "알고 있다"에서 "어떻게 우회해 개발을 계속할지"로 한 단계 더 구체화해야 함을 의미한다
3. 비용 자체보다 **약관·휴면 정책 같은 비용 인접 리스크**가 먼저 챙겨야 할 항목이다 (4.3)

이 세 가지는 모두 기술스택을 바꾸지 않고도 **기존 문서에 절과 표를 추가하는 수준**으로 해결 가능하며, 채택 여부는 사용자 판단에 맡긴다.
