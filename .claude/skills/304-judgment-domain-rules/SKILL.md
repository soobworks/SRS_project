# 판정 도메인 규칙

이 프로젝트("같이 고르기")의 정체성은 **총점을 매기지 않는다**는 데 있다. 이 스킬은 그 규칙이 가장 자주 깨질 수 있는 영역을 다룬다.

## 언제 쓰는가

- `domain/judgment/`, `domain/compromise/` 아래 코드를 작성·수정·리뷰할 때
- 조건 평가기(예산·하한형·유무형·일치형), 5분류 상태 분류기, 후보 그룹화, 완화 시뮬레이션, 양보 문장 생성을 다룰 때
- "적합도 점수", "순위", "추천 배지" 같은 표현이 요구사항이나 코드 리뷰에 등장할 때 — 대부분 이 규칙과 충돌한다

## 절대 규칙(타협 불가)

1. **여러 조건의 판정 결과를 합산·가중치화해 단일 스코어로 만드는 코드를 어떤 형태로도 작성하지 않는다** — 총점, 복합 순위, 적합도 지수 전부 금지.
2. **판정 결과는 항상 5분류 중 하나다**: `MET`(충족) / `UNMET`(미충족) / `CONFIRMATION_NEEDED`(확인 필요) / `CALCULATION_FAILED`(계산불가) / `NOT_APPLICABLE`(해당없음). 이 열거형을 임의로 축소·병합하지 않는다.
3. **후보 그룹화는 3분류로 끝난다**: 둘 다 충족 / 한쪽만 충족 / 둘 다 불충족. 그 이상의 순위·랭킹을 만들지 않는다.
4. **"확인 필요"(CONFIRMATION_NEEDED)를 다른 상태로 흡수하지 않는다.** 별도 배지로 항상 분리 노출한다.
5. **판정 로직은 순수 함수만 허용한다.** DB·외부 API 접근 금지 — 입력은 이미 조회된 데이터, 출력은 판정 결과값이다(스킬 `301-server-boundary-rules`의 Read/Write 분리 원칙).

## 코드 구조

- 평가기(`domain/judgment/evaluators/`)는 `ConditionType` enum별 레지스트리 패턴으로 등록한다 — 새 조건 타입 추가 시 이 폴더에 파일만 추가하면 되도록(REQ-NF-007).
- "출근 안 함"처럼 측정 대상 자체가 없는 경우는 `NOT_APPLICABLE`로 분기한다.
